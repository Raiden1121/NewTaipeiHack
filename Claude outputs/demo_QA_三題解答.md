# Demo 應答小抄：三題資料解讀

**資料版本**：`dev-full-youth-keyword-20260913`（目前 `current.json` 指向的 published snapshot，2026-09-13 產出）
**適用範圍**：以下數字全部直接取自 `data-pipeline/data/analytics/published/.../dashboard_overview.json`，這份 snapshot 是 deterministic pipeline 算出來的，跟 `ai-service/` 有沒有接上 Bedrock 無關 —— 就算 LLM demo 來不及，這幾題可以直接用這份小抄口頭回答。

> **關於字數限制的更新**：原始版本的「本地資料結論」「版本 A/B」段落是寫給**人看的簡報／口頭背景資料**，長度遠超過 `ai-service` 實際的輸出限制，**不能**直接當成 `answer` 欄位貼上去。查了 `ai-service/src/prompts/dataQa.ts` 才確認限制的確切位置與數字，並補上每題一則**真正符合限制、可直接當 fallback 貼上的版本**，見各題「✅ 符合 400 字限制的 answer 版本」小節。

## ai-service 的實際字數限制是什麼

寫在 `ai-service/src/prompts/dataQa.ts` 第 48 行：`export const QA_ANSWER_MAX_CHARS = 400;`，只限制 **`answer` 這個欄位**（聊天框顯示給使用者的那段話），`basis`／`limitations`／`webReferences` 等結構化欄位不算在內。用 prompt 指示而不是 schema `maxLength` 硬性驗證，原因是 code comment 寫得很清楚：驗證失敗會觸發重試，重試等於再花一次完整生成時間，反而更慢。限制 400 字是因為 API Gateway HTTP API 固定 30 秒逾時、不可調，實測 773 字要 31.5 秒（會被切斷）、580 字要 26.8 秒、479 字要 25.8 秒，400 字換算約 25 秒，留給 Lambda 冷啟動一點餘裕。**這是「硬性要求」（prompt 原文用詞），不是建議**——字數不夠時，要先砍重複與鋪陳、再砍次要指標，但「回答原本的問題」「前提更正」「樣本數警告」「相關不是因果」這四件事不可以因為字數被省略。

下面每題都附上一個**用 python `len()` 實測字數**（跟 JS 的 `.length` 在純中日韓＋半形字元的情況下算法一致）、確認 ≤400 字、且遵守上述四件事的 `answer` 版本，可以直接當 demo 現場 LLM 掛掉時的 fallback 文案。

## 0. 先講在前面：兩個重要澄清

**(1) 「宜居度」= 目前系統的「青年機會指數」（`opportunityIndex`）**
專案目前的資料模型、文件（`docs/homepage_analysis.md`、`docs/employment_analysis.md`）、前端程式碼裡都沒有「宜居度」這個欄位。三題裡對應的複合分數是首頁與青年就業頁地圖上顯示的**青年機會指數**（0–100，越高越好，綜合工作機會、薪資水準、居住友善度、交通可及、青年活力與發展五個面向）。如果現場有人問「這是不是宜居度」，可以直接回：「我們畫面上呈現的綜合分數叫『青年機會指數』，這裡指的宜居度就是這個」。

**(2) 發現一個 demo 前該修的不一致：前端公式說明文字跟實際運算權重對不上**
`frontend/src/lib/metricFormulas.ts` 顯示給使用者看的公式是：
> 機會指數 = 0.25×工作機會 + 0.25×薪資水準 + **0.25×居住友善** + 0.20×交通水準 + **0.05×人才資源**

但實際後端運算依據 `data-pipeline/config/homepage_analytics.json`（`yoi_weights`）與 `docs/homepage_analysis.md`（v9，權威文件）是：
> YOI_raw = 0.25·S_job + 0.25·S_salary + **0.15·S_talent** + **0.20·S_housing** + 0.15·S_transport

我用板橋／新莊／樹林三區的 `yoiComponents` 實際數字反推加權平均，結果精確對上「25/25/**15**/20/**15**」，對不上前端顯示的「25/25/**25**/20/**5**」（誤差達好幾分）。也就是說**畫面上的公式說明文字是舊版、已經過時**。建議 demo 前把 `metricFormulas.ts` 的文字改成一致，不然如果 AI 或口頭回答引用正確權重、畫面卻顯示錯的版本，容易被現場抓包。

## Q1：「怎麼可能新莊的宜居度比板橋還低？板橋房價那麼貴耶」

### 本地資料結論
新莊的青年機會指數（91.75，全 29 區排名第 3）確實低於板橋（100.0，排名第 1）。原因**不是**「新莊哪裡不好」，而是房價在這個指數裡的角色，跟一般人直覺的「越貴越不宜居」不一樣：

| 面向（子分數，0–100） | 板橋區 | 新莊區 | 差距貢獻（加權後） |
|---|---|---|---|
| 工作機會 S_job（權重25%） | 75.33 | 75.44 | 板橋 −0.03（幾乎打平） |
| 薪資水準 S_salary（權重25%） | 44.01 | 33.82 | 板橋 **+2.55**（最大差距來源） |
| 居住友善度 S_housing（權重20%） | 13.88 | 13.32 | 板橋 +0.11（幾乎打平，板橋反而略高） |
| 交通可及 S_transport（權重15%） | 55.26 | 46.88 | 板橋 +1.26 |
| 青年活力與發展 S_talent（權重15%） | 58.85 | 70.43 | 新莊 −1.74（新莊在這項領先） |
| **YOI_raw 合計** | **49.73** | **47.57** | 板橋領先 2.15 分 → 標準化後變成 100 vs 91.75 |

**為什麼「居住」這關板橋沒有輸，甚至還小贏？**
關鍵在於 S_housing 的組成：`0.35×租金中位數（反向） + 0.35×每坪房價中位數（反向） + 0.30×租金/薪資比（反向）`。板橋每坪房價中位數確實比新莊貴（570,463 元 vs 514,274 元），這項板橋只拿到 3.85 分（幾乎墊底）；**但青年多半是租屋、不是買房**，而板橋的租金中位數（20,000 元）反而比新莊（21,600 元）低，租金佔薪資比（0.571）也比新莊（0.618）健康，這兩項合計佔 S_housing 65% 權重，足以把「房價貴」的扣分打平甚至扳回一點點。**一句話：這個指數量的是「青年租屋負擔」，不是「買不買得起房子」，所以板橋的高房價幾乎不影響青年機會指數。**

**真正拉開差距的是薪資與交通：**
板橋薪資子分數大幅領先，主要來自「高薪職缺比例」（板橋 2.52% vs 新莊 1.27%，幾乎兩倍），而非薪資中位數本身（兩區中位數其實很接近，3.5萬上下）——板橋作為新板特區、新北市府所在地，職缺公告裡高薪職缺（門檻為全市中位數 1.5 倍以上）比例明顯較高。交通面向板橋有捷運環狀線＋台鐵三鐵共構，軌道站點密度與微笑單車站點密度標準化分數都比新莊高。新莊在「青年活力與發展」領先（青年人口佔比高、大專學生密度全市最高——新莊有輔仁大學等學校），但這項只佔 15% 權重，不足以逆轉。

## Q2：「為什麼八里區的青年薪資分數這麼高？」

2. **台北港貨櫃碼頭／物流業**：聯結車／貨櫃車司機（新竹物流、永利旺運輸，月薪 6.5–6.75 萬）、台北港貨櫃碼頭公司的機電/空調助理工程師（4.29 萬）、環春理貨的碼頭作業與資料輸入職缺（4.3–4.8 萬）。
